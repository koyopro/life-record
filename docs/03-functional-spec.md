# 03. 機能仕様

データ構造の定義は [02-data-model.md](02-data-model.md) を参照。本ドキュメントは「その構造をどう操作するか」を扱う。

## 3.1 Item

### 基本操作

- Item の作成
- Item の一覧表示
- Item の詳細表示
- Item の編集（タイトル・期限・重要度）
- Item の削除
- status の変更
- タグの付け外し（[09-tags.md](09-tags.md)）
- 繰り返しの設定（[10-recurrence.md](10-recurrence.md)）

`type` の管理機能は持たない（Item に `type` カラムを持たせないため）。

RTM 相当のソート・キーボードショートカット・SmartAdd については [08-todo-management.md](08-todo-management.md) を参照。

### 作成

スマートフォン等から素早く作成できることを最優先する。

- 入力必須はタイトルのみ
- 初期 status は `backlog`（未着手）
- 期限（`due_at`）は任意。作成時に必須としない

Item 自体は本文を持たないため、「思いついた内容を書き留めたい」場合は、Item 作成と同時に当日付の Section を1件作成する動線を用意する。

```text
入力欄1つ（タイトル）        → Item のみ作成
入力欄2つ（タイトル + 本文） → Item + 当日付の Section を同時作成
```

初期実装ではタイトルのみの最速入力を優先し、本文同時入力は任意項目として扱う。

### 一覧表示

以下の切り口で一覧できるようにする。

- status 別
- **今日**（期限が今日まで／期限切れの未完了。[08-todo-management.md](08-todo-management.md) 8.3）
- 重要度順 → 期限日順（既定。[08-todo-management.md](08-todo-management.md) 8.2）
- 期限日順（`due_at` 昇順、期限なしは末尾）
- 最終更新順

どの一覧でも「未完了 / 完了」を切り替えられる（`h`。[08-todo-management.md](08-todo-management.md) 8.4）。
やったことを見返す導線を一覧ごとに作らず、いまの絞り込みのまま裏返して見せる。

### 詳細表示

Item の詳細では、以下を表示する。

- タイトル / status / 期限 / 重要度 / タグ / 繰り返し
- メモ（`Item.note`。日付を持たない覚え書き。[02-data-model.md](02-data-model.md) 2.3）
- 紐づく Section の一覧（日付昇順、同一日付内は `position` 昇順）
- 繰り返し中なら、同じ系列の過去オカレンス
- 各 Section の日付から、対応する Diary へのリンク

Section を**古い順**に並べるのは、書き足す枠（当日の Section）を
いつも一番下に置くため（3.2）。日記と同じく上から下へ時間が流れる。

#### 分割表示（PC）

画面が広いとき（60rem 以上）は、**一覧を左に残したまま右側に詳細を出す**。
一覧と詳細を行き来せずに、次々と内容を確認できるようにするため。

**すべての一覧で共通の挙動とする。** 今日 / タスク / 検索結果（3.6）、および
今後追加する一覧も同じように振る舞う。並べ方そのものは
`ListDetailSplit` が持ち、画面ごとに書き分けない。左に何を並べるか・右に何を
出すかだけを呼ぶ側が決める（検索結果には、タスクの詳細を出せない行――日記――が
混ざるため）。

- 右ペインはカーソル位置に追従する。`j` / `k` で送ると詳細も切り替わる
- 一覧とは別にスクロールする。長い本文を読んでも一覧の位置が動かない
- 選択中の Item は URL の `selected` に残す（履歴は汚さない）。
  再読み込みしても同じ状態に戻せるようにするため
- 絞り込み（status / タグ）を変えたら選択は解除する。
  前の絞り込みで選んでいたタスクが、一覧に無いまま残らないようにするため
- 詳細が出ていないときは、一覧を読みやすい幅（40rem）に収める
- 狭い画面では従来どおり詳細画面へ遷移する
- **ダイアログ（期限・繰り返し・タグ）は body へ出す**（Vue の Teleport）。
  右ペインは `position: sticky` で、sticky は**それ自身が重なりの文脈**を作る。
  その中に置いたままでは、どれだけ z-index を上げても外の袖や「＋」より
  上に出られず、ダイアログが下に潜って隠れる
- 右ペインの上に「単体で開く」を出す。そのタスクだけのページ（`/items/<id>`）
  へ移る入口で、`Shift` + `o` でも同じところへ行ける
  （[08-todo-management.md](08-todo-management.md) 8.4）。URL をそのまま
  渡したいときや、広い幅で読み書きしたいときのため

##### カーソルは位置ではなく id で持つ

一覧のカーソルは index ではなく **行の id** で保持する。

重要度を変えるなどして並び順が変わったとき、index で持っていると
同じ位置が別の Item を指してしまい、詳細ペインが勝手に別のタスクへ切り替わる。
id で持てば、並び替えが起きても同じタスクを見続けられる。

カーソルの持ち方・送り方（`j` `k` の折り返し、指していた行が消えたときの
行き先、画面外へ出さないスクロール）は `useListCursor` に1つだけ置く。
並びも中身も違う一覧なのに送り方がそれぞれ違うと、画面を移るたびに指が迷う。

### 削除

Item を削除すると、紐づく Section も削除される（`ON DELETE CASCADE`）。
削除前に確認を挟む。

## 3.2 Section

### 位置づけ

Section は Item に対する「その日の作業ログ」。Item を分類するためのカテゴリではない。

### 基本操作

- Section の作成（Item と日付を指定）
- Section の編集
- Section の日付の変更
- Section の削除
- 同一日付内での並び替え（`position`）

### 表示

Item 詳細では、Section を**日付ごとの枠**として上から古い順に並べ、
**一番下を当日の枠**にする。

```text
2026/08/18(火)  ▾  ← 確定済み（読むだけ）
  ItemとDiaryの関係を整理した。
2026/08/19(水)  ▸  ← トグルで隠せる
2026/08/20(木)  ▾
  昨日の続きでリンクを確認した。
2026/08/21(金) 今日 ● ← ここだけが入力欄
  ┌──────────────────────┐
  │ 今日やったこと          │
  └──────────────────────┘
```

かつては「本文」と「日々の作業記録」を分けて出していたが、**本文の枠には
日付が固定で付いていた**ため、日をまたいで書き足すと最初の日の記録が
太っていくだけになり、どの日に何をしたのか分からなくなっていた。
枠を日付で分ければ、書き足した内容はその日の記録として残る。

#### 当日の枠

- 画面を開いた日の Section を編集する。**その日の記録がまだ無ければ空で出し、
  何か書かれた時点で作る。**開いただけの日が記録として残らないようにするため
- 開いたまま日付をまたいだら、当日の枠は新しい日付に切り替わる。
  それまで書いていた分は、その日の記録として上へ回る
- 同じ日に複数の記録があるときは、**最後の1件**が当日の枠になる
  （別の端末で同じ日に書かれた場合など）

#### 過去の記録

- **確定済みの見た目**で出す（入力欄の枠は出さない）。読み返すためのものが
  入力欄の形で並んでいると、どれが今日書く欄なのか分からなくなる
- トグルで中身を隠せる。日をまたぐ記録が増えると、当日の枠が下へ遠のくため
- いつの記録かはトグルに日付を載せる。畳んでいても分かるようにする
- **編集アイコン**を押した記録だけが書ける状態になる。日付の変更・並べ替え・
  削除も、編集中にだけ出す

#### 一覧カードの本文

一覧カードに出す本文（`ItemDto.body`）は**最初に作られた Section**のままで、
当日の枠を書いても入れ替わらない（[02-data-model.md](02-data-model.md) 2.4）。
詳細で `⌘` + `C` に写るのもこちら。一覧と詳細で同じキーが違うものを
写すと、どちらが写ったのか分からなくなるため。

### 作成

- **基本は当日の枠に書くだけ**で、Section はそこから自動的に作られる（上の「表示」）。
  一覧からは `y` で当日の枠へ移る（[08-todo-management.md](08-todo-management.md) 8.4）
- 記録の一番下に「作業記録を追加」を置く。**日付を選んで作れる**ので、
  当日以外の記録もここから足せる（数日前にやったことを後から書くときのため）。
  日付の既定は当日で、触るまでは当日に追従する
- 追加した記録が当日なら当日の枠へ、それ以外ならその記録を編集状態で開いて
  フォーカスする。作った直後にそのまま書き始められるようにするため

#### 1つのタスクの記録は、同じ日に1件だけ

**1日の作業は1つの記録にまとめる。**その日に何をしたのかを読み返すときに、
同じ日付の枠が並んでいると追いにくいため。

- 「作業記録を追加」で選んだ日にすでに記録があれば、**作らずにその記録へ移る**
- 日付を変えた先にすでに記録があるときは、**1つにまとめる**（下の「日付の変更」）
- 書いたものは捨てない。まとめるときは本文を続けて書き足す

DB には一意制約を置かない。別の端末で同じ日に書かれた分は、送られた時点で
同じ日に2件になりうる（オフラインで書けることを優先する。
[12-offline.md](12-offline.md) 12.5）。そのときは並べて出し、日付を変えれば
まとめられる。

### 日付の変更

作業した日を後から書き足すことがあるため、日付は作成後も直せるようにする。
日付を変えると並び順のグループも変わるので、移した先の日付の末尾へ置く。

日付を直せるのは**編集アイコンで開いている間だけ**にする。読むだけの見た目に
日付の入力欄が出ていると、触るつもりのないものを動かしてしまう。

当日の枠は常に書ける枠なので、代わりに**日付を押したときだけ**入力欄にする。
日付は読み返すときにいちばん見る文字なので、既定は曜日つきの読みやすい表示の
ままにしておく。当日の枠の日付を変えると、その記録は変えた先の日付の記録として
上へ回り、当日の枠は空に戻る。

移した先にすでに記録があるときは、同じ日に2件にせず**1つにまとめる**。
まとめると片方の記録が無くなるので、まとめてよいか必ず確認する。本文は
移す側を後ろに書き足す（時間の流れと同じ向きに並ぶ）。

### 並び替え

同じ日付の記録どうしでのみ並べ替える（`position` の定義による）。同じ日に
1件だけなら並べ替えるものが無いので、**同じ日に複数ある記録**（前からある分や、
別の端末で書かれた分）のためだけに残している。
並びは1件ずつではなく、その日付の記録の順序をまとめて送る。
1件ずつ position を送ると、途中で失敗したときに番号が重複したまま残るため。

### 本文

**Scrapbox 記法**で記述する（[11-scrapbox-notation.md](11-scrapbox-notation.md)）。
Markdown ではない。画像の埋め込みに対応する（3.5 参照）。

### 保存

**保存ボタンは置かない。** 入力が止まったところで自動的に保存する。

- 入力が止まってから約 0.7 秒後に保存する
- 保存中の状態（未保存 / 保存中 / 保存しました）を小さく表示する
- 画面を離れる・タブが隠れるときは、待たずに即座に保存する
- 保存が前後しないよう、前の保存が終わってから次を送る

これは Item のタイトルにも同じく適用する。書いた内容が保存されたか気にせずに済むことを優先する。

**1行で書く欄（タイトル・URL）は `Enter` を確定として扱う。** 待ち時間を挟まずに
保存し、フォーカスを外す。押すボタンが無い以上、書き終わったと伝える手が `Enter`
しかなく、そこで何も起きないと入力が終わったのかどうかが分からないまま欄に留まる。
日本語入力の変換を確定する `Enter` は拾わない（変換中は素通りさせる）。

## 3.3 Diary

日記は日付を基本単位とする。1日1件。

### 基本操作

- Diary の作成 / 編集（日付を指定して開き、本文を書く）
- Diary の閲覧
- 日付を指定して過去の日記を開く
- 日記一覧（月のカレンダー）

### UI

- `/diary/month/YYYY-MM` が月のページ（カレンダー）、`/diary/YYYY-MM-DD` が
  その日のページ。`/diary` は開いた時点の月へ送るだけ（`/diary/today` と同じ
  振り分け）
- **袖（3.9）の「日記」は、その日の日記（`/diary/<今日>`）へ入れる**
  （`g` `d` と同じ行き先）。日記は開いて書くものなので、カレンダーを
  経由させると必ず1タップ余分になる。ホーム画面アイコンの長押しからも
  同じ場所へ入れる（`/diary/today`。[14-app-shortcuts.md](14-app-shortcuts.md) 14.1）
- 日ページのヘッダーは**1行**にまとめる。並びは
  「← 前の日 / 日付 / 🗓️ / 次の日 →」で、狭い画面（30rem 以下）では
  前後の移動を矢印だけにする（文字まで入れると日付が押し出されて2行になる）
- 前後の日へは `h` / `l` でも移れる（一覧の `j` / `k` と同じく vi の並び）。
  本文を書いている間は効かない（入力欄ではショートカットを無効にする。
  [08-todo-management.md](08-todo-management.md) 8.4）
- 別の日へは 🗓️ からカレンダー（`/diary`）に移って選ぶ。日ページに
  日付の入力欄（`<input type="date">`）もカレンダーも持たない。
  1行に収めるためと、選ぶ導線を1か所にまとめるため
- 対象日の Diary が存在しなければ、新規作成として空の状態で開く。
  未作成の日を 404 にすると、開いてそのまま書き始められない
- 保存時に upsert する（`date` が主キーのため）
- 本文は Section と同じくリアルタイム保存とする（3.2）。
  日付を移る前には、待たずに保存してから遷移する

### 一覧はカレンダー

`/diary/month/YYYY-MM` は**月のカレンダー**で見せる。日記は日付が主キーで、
「どの日に書いたか」がそのまま中身の意味を持つため。書いた日だけを
縦に並べると、空いている日が詰められて見えず、続いているのか
飛んでいるのかが分からない。

- 日曜始まりの月表示。前後の月の日も升目に出す。
  週の途中で欄が欠けると曜日の列がずれ、カレンダーとして読めなくなる
- 日記のある日は点で示す。升目に本文を詰めると、狭い画面で日付が読めない
- 升目のサムネイルは次の順で選ぶ
  1. **日記の本文**にある最初の画像
  2. 無ければ、**ピン留めした作業記録**にある最初の画像（上に出ているものが優先）

  本文を書いていない日でも、ピン留めに画像があればその日を出す。ピン留めは
  「その日の目印」なので、本文を書いた日だけに出しても目印にならない。
  抜粋（文字）は本文からだけ作る
- 今日の升目は枠で示す
- 表示中の月は URL（`/diary/month/YYYY-MM`）そのものに持たせる。
  戻る操作と再読み込みで同じ月に戻れるようにするためと、
  **本文からその月を指せるようにするため**（下記）
- カレンダーの下に、その月の日記を日付降順で並べて抜粋を読めるようにする

一覧 API（`GET /api/diaries`）は `from` / `to` で期間を絞れる。
件数で絞ると、古い月を開いたときにその月のぶんが返らない。

### この月を指しているもの

月のページの下に、**本文からこの月を指しているもの**を並べる。月の振り返りを
書いたタスクと月のページが、これだけで相互に行き来できる
（[11-scrapbox-notation.md](11-scrapbox-notation.md) 11.11）。

- 保存するのは、本文に書いた `[/diary/month/YYYY-MM]` という1方向のリンクだけ。
  逆向きは `Item.note` / `Section.body` / `Diary.body` を部分一致で引いて
  導き出す（`GET /api/backlinks`）。**中間テーブルもカラムも増やさない**
- タスクの状態では絞らない。「このページを指しているものが他にあるか」を
  漏れなく見たいため。月の振り返りは、済んだタスクから指されているのが普通
- 各行には、指してきた本文の**冒頭5行**を添える。記法はそのまま返し、画面で
  解釈して出す（「この日にやったこと」の作業記録と同じ見せ方・同じ行数
  `WORKED_ON_HEAD_LINES`）。リンクを書いた箇所の前後ではなく**頭から**出すのは、
  指してくるものが月の振り返りのように「1枚の読みもの」であることが多く、
  リンクのまわりだけを切り出しても何の話か分からないため
- リンクを打たずに済むよう、月のページに
  「振り返りを作る」（題とリンク入りのタスクを作る）と
  「リンクをコピー」（記法をクリップボードへ）を置く。書きながらなら
  `Ctrl`+`T` を続けて3回でも入る
- 検索と同じくサーバーにしか無いので、オフラインでは出ない
  （[12-offline.md](12-offline.md)）

### 空にしたら消す

本文が空になったら行ごと削除する。書きかけて消した日が、
空のまま一覧に並び続けないようにするため。

### その日に作業したTODOの表示

Diary 画面の下部に、同じ日付を持つ Section から導出した Item 一覧を表示する。

```text
2026-08-18の日記

今日は個人用アプリの設計を進めた。


── タグなし ──

読書メモ
  『データ指向アプリケーション設計』の3章まで

── 仕事 ──

個人用アプリのDB設計
  Section を日付で分ける方針にした
  position は同一日付内の並び順にする
  …

TODO管理の見直し
  RTM から移す項目を洗い出した
```

**タグごとにまとめる。**1日を振り返るときに見たいのは「何に時間を使ったか」で、
いまの状態（完了かどうか）ではないため。複数のタグが付いた Item は
**そのすべてのグループに出す**（片方のタグからだけ見えないと取りこぼす）。
グループの見出しはタグ名で、行には見出しに出ていない方のタグだけを添える。

**タグの付いていないものを先頭に置く。**分類の手がかりが無いぶん、下に置くと
埋もれるため。その後ろにタグ名順で並べる。

**作業メモの無い Item は出さない。**日記に並べたいのは「何をしたか」で、
記録の枠だけがあって中身の無いものは読み返す手がかりにならない。その日に
完了しただけ・記録を作っただけの Item は、ここには出てこない。

#### ピン留め

その日の作業記録は、**ピン留めすると先頭にまとめて出る**。1日に何件でも
留められる。振り返って読むときに目当ての記録がタグのグループへ散っていると、
上から順に探し直すことになるため。

```text
── 📌 ピン留め ──

牛乳を買う
  帰りにスーパーへ

── 仕事 ──
…
```

- 留めたものは**タグのグループには出さない**。上と下の2か所に同じ記録が
  出ると、読み返すときに数え直すことになる
- ピン留めの中の並びは、他のグループと同じ（Item の更新が新しい順）
- 印は作業記録（Section）が持つ（[02-data-model.md](02-data-model.md) 2.4）。
  **DB に入るので、別のブラウザ・別の端末でも同じ並びで出る**
- 手元（IndexedDB）へ先に書き、送信は列へ積むだけなので、オフラインでも
  留められる（[12-offline.md](12-offline.md)）。送るのは本文の保存と同じ
  経路（`section_save`）で、ピン専用の操作は作らない。分けると、本文の保存と
  前後して届いたときにどちらが勝つのかが決められない
- 同じ日に複数の記録がある Item（別の端末で書かれた分など。3.2）は、日記では
  1件にまとめて出しているので、ピンも元になった記録すべてに当てる

**その日の作業記録も、冒頭5行まで添える。**タイトルだけでは何をした日か
思い出せないため。全文を出すと日記そのものより長くなるので冒頭だけにし、
続きがあることは `…` で示す。続きは Item 詳細で読む。記法はそのまま解釈して
出す（落とすと箇条書きや画像がただの文字になって読みにくい）。

各 Item はリンクとし、Item 詳細へ遷移できるようにする。

逆向きにも辿れる。Item 詳細では、本文と各作業記録の日付から
その日の Diary へ移れる（3.1 / [02-data-model.md](02-data-model.md) 2.8）。

## 3.4 整理フロー

### 追加

スマートフォン等から Item を素早く作成する。初期状態は `backlog`（未着手）。

### 整理

後から Item を確認し、以下の形で整理する。

- 不要なら削除
- 対応中なら `in_progress`
- 完了したら `closed`
- 作業した内容があれば、その日付の Section を書く

分類には **タグ**を使う（[09-tags.md](09-tags.md)）。`status`（進行状態）とタグ（内容による分類）は
役割が異なるため併存する。タグは Milestone 4 で導入するため、それまで整理は status のみで行う。

## 3.5 画像

Scrapbox のように、本文中へドラッグ&ドロップ等で画像をアップロードできるようにする。

対象は `Section.body` と `Diary.body` の両方。

自分で登録するアイコン（`:name:`。[11-scrapbox-notation.md](11-scrapbox-notation.md) 11.8）も
この経路をそのまま使う。アイコンのための置き場は別に作らない。

### 保存先

**Amazon S3** を採用する。

採用理由:

- 長期的な安定性
- 一般的なオブジェクトストレージであり、将来的な移行がしやすい
- 画像データとアプリケーションDBのデータを分離できる

日記用途も含むため、画像は10年以上の長期利用を想定して保存する。

### アップロードフロー

1. ユーザーが画像をドラッグ&ドロップ（またはスマートフォンから選択・撮影）
2. フロントエンドが API に対してアップロード用の署名付きURL（presigned URL）を要求
3. フロントエンドが S3 へ直接 PUT する
4. アップロード成功後、本文中に画像参照を Scrapbox 記法で挿入する（[11-scrapbox-notation.md](11-scrapbox-notation.md) 11.7）
5. 表示時は、その参照から画像を読み込む

Vercel の Function を経由して画像バイナリを転送せず、**S3 へ直接アップロードする**方式とする（実行時間・ペイロードサイズの制約を避けるため）。

### 参照方法

本文には `[/images/<ID>.<拡張子>]` を書き、表示時にアプリが
S3 の署名付き取得URLへリダイレクトする（[07-open-questions.md](07-open-questions.md) Q4）。

```text
POST /api/images        署名付きの PUT 先を発行する（画像は通らない）
PUT  <署名付きURL>       ブラウザから S3 へ直接
GET  /images/<ID>.<拡張子>   → 302 → S3 の署名付き取得URL（5分）
```

本文に有効期限つきの URL を書かないので、期限切れで画像が失われない。
ホスト名も書かないため、ドメインを変えても本文はそのまま使える。

### 入力

- PC — 本文へのドラッグ&ドロップ、クリップボードからの貼り付け
- スマートフォン — 本文の「画像を追加」から選択・撮影

いずれも、アップロードが終わってから本文へ記法を差し込む。
差し込み先は編集中の行の次の行（書きかけの文を割らないため）。

### 画像の削除

本文から画像参照を消しても S3 のオブジェクトは残る。
初期実装では S3 上の孤児オブジェクトを許容し、整合性の担保は後回しにする。将来的に以下を検討する。

- 画像メタデータテーブルを持ち、参照カウントを管理する
- 定期的に本文をスキャンして未参照オブジェクトを検出する

## 3.6 検索

検索は重要な機能だが、**最初のマイルストーンには含めない**。

### 対象

```text
検索
├── Item.title
├── Item.note（メモ）
├── Section.body
└── Diary.body
```

メモも Item 自身の中身なので、タイトルと同じ扱いで拾う。行の見出しには
タイトルが出るので、抜き出して見せる（excerpt）のはメモのほうにする。

### 絞り込み

- 対象の限定（タスク名 / 作業記録 / 日記）
- タスクの「未完了 / 完了」（既定は**未完了**）
- 日付による絞り込み
- タグによる絞り込み（[09-tags.md](09-tags.md)）

`type` によるフィルタは、`type` カラムを持たないため対象外とする。

タグは Item に付くもので、日記には当てはまらない。**タグで絞ったときは、
結果に日記を混ぜない。** 絞り込みの対象外という理由で、日記だけが素通り
するのは分かりにくいため。

#### 未完了 / 完了

一覧（[08-todo-management.md](08-todo-management.md) 8.4）と同じ切り替えを置き、
**既定は未完了**にする。片付いていないもののうち「あれは何だったか」を探すのが
普段の使い方で、完了したタスクが混じると目当てのものが埋もれるため。
状態は一覧と同じ `?completed=true` に置く。

- 進行状態（未着手 / 対応中 / 完了）そのものでは絞らない。一覧が
  「未完了をひと続きで見る」を採っているのに、検索だけ別の軸を持つ理由がない
- 一覧の「すべて」に当たる見方は持たない。検索は元から言葉で絞った結果なので、
  状態でも絞らない見方は結果が広がりすぎる
- **この切り替えでは日記を外さない。** タグと違って常に効いている見方なので、
  外すと既定の検索から日記が丸ごと消えてしまう。日記は状態を持たないまま、
  どちらの見方でも出る

### 並び

日付の新しい順に混ぜる。日付は種別ごとに以下を使う。

| 種別 | 日付 |
|---|---|
| Item | 作成日 |
| Section | `date`（作業日） |
| Diary | `date` |

### 抜粋

本文の先頭ではなく、**一致した箇所の前後**を切り出す。
長い本文では、先頭から出しても一致箇所が見えないため。

### 表示

Item と Diary は別概念のまま維持しつつ、検索UIでは横断して結果を表示する。

```text
「DB設計」

2026-08-18  日記
今日はDB設計について考えた。

｜個人用アプリのDB設計  仕事           明日
  タスク

｜個人用アプリのDB設計  仕事           明日
  2026-08-18  作業記録
  DB設計のテーブル構成を検討した。

2026-08-19  日記
昨日考えたDB設計を整理した。
```

**タスクの行は、一覧とまったく同じカード（`ItemCard`）で出す。** 似せるのでは
なく同じ部品を使う。探し当てたものが一覧で見ているのと違う顔つきだと、同じ
タスクだと結び付けるのに一拍かかるうえ、そこからできることも別に覚えることに
なるため。

カードに渡すのは**手元（IndexedDB）の Item そのもの**で、検索の応答ではない。
応答をそのまま描くと、完了にしたりタグを外したりしても行が古いままになる。
まだ手元に無いとき（他の端末で作られた直後など）だけ、応答から最小限を
組み立てて出す。

- **タスク名で当たった行には作成日を出さない。** いつ作ったかは探すときの
  手がかりにならず、カード右端の期限と2つの日付が並んで読み取りにくくなる
  （並べ替えには引き続き作成日を使う。上の「並び」を参照）
- 作業記録で当たった行は、カードの下に**日付と抜粋を1行**添える。何がどこに
  書いてあって当たったのかは、カードだけでは分からないため。カードとの間の
  罫線は消してひと続きに見せる（区切ると、下の1行が次の結果に見える）
- 日記の行は、カードと同じ密度で並べるが重要度の帯・チェック・期限は出さない。
  どれも Item に付くもので、日記は持たないため
- 完了にしても、その行は結果から消えない。結果の中身を決めたのはサーバーで、
  手元では絞り直せないため。取り消し線の付いたカードが残る（次に検索し直せば
  消える）

### 結果の選び方

**探した結果をその場で片付けられるようにする。** 見つけて終わりではなく、
たいていはそのまま状態を変えたり期限を動かしたりしたい。そのため、一覧
（3.1「分割表示」）と同じ形にする。

- 広い画面では**左に結果・右にタスクの詳細**を並べる（`ListDetailSplit`）。
  選択は一覧と同じく URL の `selected` に残す
- `j` / `k`（`↑` / `↓`）で結果を送り、`o`（`Enter`）で開く。打鍵は一覧と
  そろえる（`useListCursor`）
- **編集の打鍵も一覧と同じものが効く**（完了・状態・重要度・期限・タグ・
  くり返し・削除・取り消し・チェックしてまとめて操作）。同じ部品
  （`ItemActions`）を付けているので、一覧で覚えたことがそのまま使える
  （[08-todo-management.md](08-todo-management.md) 8.4）
- カーソルが日記の行にある間、操作の対象は**空**になる。指していない
  タスクに `c` や `Delete` が効いてしまわないようにするため
- **日記の行は右ペインに、読むだけで出す**（`DiaryPreview`）。書く場所は
  日記のページ1つに保つ。2か所から同じ本文を編集できると、保存の行き先が
  分かりにくくなるため。探している最中に中身を確かめられれば足りる
- 行はリンクのままにしておき、右ペインで開けるときだけ遷移を止める。
  ⌘ + クリックや中クリックで別タブに開けるようにしておきたいため

#### 入力欄と結果の行き来

**`Enter` で検索を実行したら、入力欄からフォーカスを外す。** 打ち終わったら
結果を見るのだから、そのまま `j` / `k` へ移れるようにする（入力欄に
フォーカスがある間、画面の割り当ては効かない。
[08-todo-management.md](08-todo-management.md) 8.4「自前でキー操作を持つ場所には
手を出さない」）。
スマートフォンではキーボードも下がる。

- 待ち時間（0.3秒）は挟まずにその場で投げる。日本語入力の変換を確定する
  `Enter` は拾わない
- 打ち直すときは `/` で入力欄へ戻り、いまの語を選択した状態にする。
  `Enter` で欄を離れたあと、キーボードだけで往復できるようにするため
- **すでに結果が出ている状態で開いたとき**（`?q=` 付きのリンク、戻ってきた
  とき）は、入力欄へフォーカスを入れない。読みたいのは結果のほうで、
  ここにフォーカスがあると `j` / `k` が打てない

### 実装方針

データ量が小さいうちは `ILIKE` による部分一致で十分。
`%` `_` `\` は `ILIKE` のメタ文字なので、エスケープしてから渡す。
将来的に PostgreSQL の全文検索（`tsvector` + GIN インデックス）を検討する。日本語対応のため `pg_bigm` 等が必要になる可能性があるが、Neon での拡張の利用可否は要確認。

## 3.9 画面の構成（左袖）

**移動の入口は左袖（`AppSidebar`）だけ**にする。RTM の左側に合わせる。

以前は上に区分の帯（今日 / タスク / リスト / タグ / アイコン / 日記 / 検索）を
置いていたが、袖を持つと同じ行き先が2か所に並ぶ。狭い画面では帯と画面の見出しで
2行が埋まり、一覧が始まるまでが遠かった。帯はやめ、行き先はすべて袖に入れる。

```text
全てのタスク            /
今日                 3  /today
検索                    /search
日記                    /diary/<今日>
  4日前 … 当日          /diary/<日付>（当日を末尾に5日ぶん）
リスト                  /lists
  （作ってあるリスト）  /lists/<id>
タグ                    /tags
  （使っているタグ）    /?tag=<名前>
--- 下の段（袖の下端に貼り付ける） ---
アイコン                /icons
表示テーマ              （ThemeToggle）
```

毎日押すものを上に、持ち物の管理（アイコン・表示テーマ）を下の段に分ける。
下の段はタグが増えて中身が流れても、袖の下端に残る（`position: sticky`）。

一覧の中身まで出しておくのは、**一覧から一覧への移動を1押しで済ませる**ため。
`g` `s` / `g` `m` は名前を打って直接移る入口（8.4）で、こちらは
「何があるか見てから選ぶ」ときの入口。どちらも行き先は同じ URL なので、
片方だけが持つ場所は作らない。

- 日記は**当日を末尾にした直近5日**を出す。書くのはたいてい今日か、
  書きそびれた直前の数日なので、カレンダー（`/diary`）を開かずに済む。
  開いたまま日付をまたいでも `useToday` が切り替わるため、翌日はその日を
  末尾にした5日分になる
- リスト・タグは見出しを押せばそれぞれの一覧画面（`/lists` / `/tags`）へ移る。
  作る・消す・色を変えるといった編集はそちらで行い、袖は移動だけを持つ
- タグには件数と色を添える。`/tags` と同じく**未完了の件数**なので、
  押した先に並ぶ数と一致する
- 「今日」にも件数を添える。押した先（`/today`）が開いたときに並ぶもの、
  つまり**期限が今日までに来ている未完了**を数える。ここだけ数字が無いと、
  他は数えられていて「今日」は数えられない欄なのだと読めてしまう。開いた
  まま日付をまたげば数え直る（[08-todo-management.md](08-todo-management.md) 8.6）
- リストにも件数を添える。こちらは**そのリストの表示方法**（未完了 / 完了 /
  すべて）で数える。タグと同じく「押した先に並ぶ数」に揃えるためで、
  既定の「未完了」で作ったリストならそのまま未完了の件数になる
  （[08-todo-management.md](08-todo-management.md) 8.6）
- 見出しの左の ▾ で折りたためる。タグは数が増えるので、畳んでおけるようにする

### 開閉

`;`（RTM と同じ）と、ハンバーガー（☰）で開閉する。狭い画面では、
**画面の左端からのスワイプ**でも開ける。

- 広い画面（60rem 以上）では**本文の横に並べる**。開いている間、本文は
  袖の幅ぶん右へ寄る。初めて開いたときはこの幅なら出しておく
- 狭い画面では**本文に重ねて**出す。背景・`Esc`・行き先を押せば閉じる。
  本文を寄せると画面の外へはみ出すため、こちらでは寄せない
- 開いているかどうかは端末ごとに localStorage へ控える。並びの設定
  （[15-client-state.md](15-client-state.md) 14.7）と違いサーバーへは送らない。
  画面の広さで見え方が変わる以上、机の上で開いたことを電話へ持ち込む
  理由がないため
- 閉じている間は画面の外にあるだけなので、`inert` で Tab の行き先からも外す

#### 左端からのスワイプ（一覧の画面）

狭い画面で袖を開く入口は左下の ☰ だけだった。一覧を眺めながら別の一覧へ
移りたいとき、そのたびに親指を左下まで下ろすことになる。端からのスワイプなら、
いま指を置いている高さのまま引き出せる（`useSidebarSwipe` /
`app/utils/edge-swipe.ts`）。

- **指の動きにそのまま袖を追わせる。** どこまで引けば開くのかが途中で分かり、
  途中でやめれば閉じたところへ戻る。触れた瞬間に開ききる作りだと、うっかり
  触れたのか自分で開いたのかが区別できない。背景の濃さも引いた分だけにする
- 端と見なすのは左 24px。Android の「戻る」ジェスチャと同じくらいにする。
  広く取ると、一覧の左端にある選択の四角（[08-todo-management.md](08-todo-management.md) 8.4）を押しづらくなる
- 64px まで引いて離せば開く。届かなければ戻す
- 縦へ動かしたら一覧のスクロールとして手を引く。どちらへ動かしたいのかが
  分かるまで（8px）は袖を動かさない。触れた直後の数 px で決めると、
  縦に送るつもりの指でも袖が顔を出す
- **一覧を出している画面（`ItemListView`）だけ**に付ける。日記や詳細の本文では
  文字の選択と取り合いになるうえ、そこから戻りたい先は袖ではなく元の一覧
  （`useListOrigin`）なので、端のスワイプを当てる意味が薄い
- 並べて置ける幅（60rem 以上）と、すでに開いている間は引かない
- 端から始まったスワイプは `ItemCard` では拾わない。両方で拾うと、袖が出ながら
  そのタスクまで完了してしまう

### ☰ の置き場所

☰ は**画面の流れには入れない**。1行ぶんの高さを取ると、帯をやめて本文を
上へ詰めた意味がなくなるため。置き場所は幅で変える。

- 広い画面（60rem 以上）… 左上に浮かべ、その幅ぶん（3rem）だけ本文の左を空ける。
  袖を開いたときの ☰ と**同じ場所**なので、開け閉めしてもボタンが飛ばない
- 狭い画面 … 右下の「＋」と対にして**左下**に浮かべる。上に置くと画面の見出し
  （「タスク」「未完了 / 完了」）と重なり、避けるために左を空けると一覧が細くなる。
  下端なら縦も横も取らず、片手で届く。選択中は下端の帯（8.4）と重なるので、
  「＋」と同じく退ける
