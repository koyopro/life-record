# 14. クライアントの状態管理

編集した内容を、画面をまたいで即座に出すための決まりごと。

**編集した結果はストアに置く。画面はストアだけを読む。サーバーへの送信は
ストアが裏で行う。**

## 14.1 なぜ要るか

編集してから別の画面へ移り、戻ってくると編集前の内容が一瞬（電波が悪いと
数秒）見える、という問題が繰り返し起きていた。原因はどれも同じで、

- 画面が `useFetch` の結果とセッション内の控えの**2つ**を見ていた
- 書き込みは `$fetch` でサーバーへ送るだけで、**読み取り元を更新していなかった**
- 編集中の値がコンポーネントの `ref`（下書き）にあり、**画面を離れると消えた**

その結果「どちらか片方だけが新しい」状態ができ、戻ったときに古い方が出た。
場所ごとに手当てを足すと、手当ての数だけ抜けが残る。

## 14.2 決まりごと

### 1. 画面はストアだけを読む

`useFetch` / `$fetch` を `pages` と `components` に置かない。取得はストアの
`track()` の中だけで行い、結果もストアの控えへ入れる。読む場所が1つなら、
「片方だけ新しい」状態は作れない。

### 2. 書き込みもストアを通す

編集はストアの操作（`editTodayBody` など）を呼ぶ。ストアが控えへ即座に反映し、
送信を予約する。画面はサーバーの応答を待たない。

### 3. デバウンスするのは送信であって、ローカル反映ではない

打鍵はそのままストアへ渡し、**その場で IndexedDB に書く**。遅らせるのは
送信（列を流すこと）だけで、0.7秒静かになってから走らせる。

こうすると下書き（`xxxDraft`）が要らなくなり、「編集中はサーバーの内容で
上書きしない」というコンポーネント側の手当ても要らなくなる。送信の予約は
ストア（モジュール）に残るので、送る前に画面を移っても続く。書いたものは
IndexedDB と未送信の列に残るので、**送る前にページごと消えても失われない**
（[12-offline.md](12-offline.md)）。

### 4. サーバーの内容を重ねるとき、手元の方が新しい本文は残す

取り直した内容を当てるときは、**手元の方が新しい本文だけ**ローカルを残し、
それ以外（日付・並び順・記録の増減・メタデータ）はサーバーを採る。丸ごと
捨てると、書いている最中に触っていない部分まで古いままになる。

「手元の方が新しい」は、記録ごとに次のどちらかで判断する
（`app/utils/offline/body-repository.ts`）。

1. まだ送れていない（同期状態が `synced` 以外）。送信待ち・送信中・
   送れなかったものは、すべてここに入る
2. 送れているが、**応答を作った時刻より後に保存できている**

2 が要るのは、取得（GET）と保存（PUT）が別々に飛ぶため。**保存より前に出した
取得の応答が、保存の後で届く**ことがあり、その内容にはこちらの保存が入って
いない。1 の守りは送り終わった瞬間に外れるので、これだけでは「書いた内容が
少し経ってから消える」が起きる（待ち時間の長い回線ほど起きやすい）。

そのため、`GET /api/items/:id` と `GET /api/diaries/:date` は応答を作った時刻
（`fetchedAt`）を返し、手元の記録が持つ更新日時（同期済みならサーバーが
打った時刻）と比べる。比べるのはどちらもサーバーの時刻なので、端末の時計が
ずれていても狂わない。

記録の増減も同じ考え方で重ねる。応答に無い記録は他の端末で消されたものとして
落とすが、**その日の最初の打鍵で作った記録**（応答より後に保存したもの）と、
まだ送れていない記録は残す。

`mergeServerItems`（TODO 側）が未送信の変更を上書きしないのと同じ規則。

### 5. 写しは、写した先も一緒に更新する

`ItemDto.body` は先頭 Section の本文の写しで、IndexedDB にも入っている
（一覧カードの抜粋、`⌘` + `C` でのコピー元）。先頭 Section を保存したら、
この写しも更新する。しないと、次にサーバーから取り直すまで古い本文が残る。

先頭 Section の決め方はサーバーと同じ規則（`app/utils/section-order.ts`）で
手元でも計算できるので、応答を待たずに揃えられる。

### 6. その日の記録は、何か書かれてから作る

詳細で書く枠は**その日の Section** で、日をまたげば別の枠になる
（[03-functional-spec.md](03-functional-spec.md) 3.2）。その日の記録がまだ
無いうちに空の Section を作ると、開いただけの日が記録として残ってしまう。
そこで**最初の一文字で id を決めて作る**（id は手元で発行する。
[12-offline.md](12-offline.md) 12.6）。

以前は送信の時点まで Section を作らず、それまでの打鍵を別の下書きに置いて
いた。手元に置き場（IndexedDB）ができたので、その場で作れば足りる。

## 14.3 層

```text
pages / components        読む（computed）／書く（ストアの操作）だけ
        ↓
ストア                     useItemStore       … TODO のメタデータ
                          useItemDetailStore … 作業記録（Section）
                          useDiaryStore      … 日記
        ↓ 即座に反映                    ↓ 送信は遅らせて裏で
IndexedDB（唯一の読み取り元）    SyncQueue → sync-engine → API
```

| ファイル | 役割 |
|---|---|
| `app/utils/offline/body-repository.ts` | 本文の読み書きと、サーバーの内容の重ね方。Vue 非依存 |
| `app/utils/offline/body-actions.ts` | 「ローカルへ書く」と「操作を積む」を1組にしたもの |
| `app/utils/save-scheduler.ts` | 鍵ごとの遅延送信と保存状態（タイトルの `useAutosave` が使う）。Vue 非依存 |
| `app/utils/section-order.ts` | Section の並び・先頭 Section・当日の枠の決め方（サーバーと同じ規則） |
| `app/composables/useToday.ts` | 「今日」。開いたまま日付をまたいだら切り替わる |
| `app/composables/useItemDetailStore.ts` | 本文・作業記録の唯一の入口 |
| `app/composables/useDiaryStore.ts` | 日記の唯一の入口 |

## 14.4 TODO のメタデータとの違い

TODO のメタデータ（タイトル・状態・期限・タグ）は、送るときに競合を確認する
（`baseUpdatedAt` を添え、サーバー側が新しければ 409。[12-offline.md](12-offline.md) 12.5）。

**本文は競合を確認しない。**最後に書いたものがそのまま残る。文章は項目ごとの
突き合わせができず、どちらか一方を捨てるしかない以上、「いま書いた方を残す」が
いちばん驚きが少ないため。

置き場（IndexedDB）と送り方（SyncQueue）は同じなので、オフラインで書けること・
送れなかった分が残ることは、どちらも変わらない。

## 14.5 状態管理ライブラリ

Pinia は入れていない。今回の問題は「置き場が無いこと」ではなく
「書き込みが読み取り経路を通っていないこと」だったため、層を整えるだけで
解消した。入口が `useXxxStore()` に揃っているので、必要になったときに
中身を差し替えれば移せる（[04-architecture.md](04-architecture.md) 4.3）。

## 14.6 テスト

`npm test`。画面から切り離せる層だけを対象にする。

- `tests/save-scheduler.spec.ts`: 途中の値を送らない、同じ鍵で追い越さない、
  失敗を握り潰さない、flush
- `tests/offline/body-repository.spec.ts`: 未送信を上書きしない、古い応答で
  戻さない、消えたものを消す
- `tests/offline/body-sync.spec.ts`: 打鍵をまとめて1つの操作にする、送るのは
  送信時点の内容、オフラインで書いて繋がってから送る
- `tests/section-order.spec.ts`: 並びと先頭 Section が、サーバーと同じ結果になる
- `tests/offline/todo-repository.spec.ts`: 本文の写しの差し替え（`setItemBody`）

画面をまたぐ挙動（編集 → 別画面 → 戻る）はブラウザでの確認になる。取り直しの
最中を見たいので、DevTools の Network を Slow 3G にしてから行う。

1. 本文を書いて一覧へ戻り、開き直して編集前の本文が出ないこと
2. 書いた直後（1秒以内）に画面を移っても、サーバーに届いていること
3. 日記を書いて別の日へ移り、戻って編集前の本文が出ないこと
4. 書いた直後に再読み込みしても内容が残り、そのまま送られること
4. 日記を書いて一覧（カレンダー）へ戻り、プレビューが編集後になっていること

## 14.7 画面の設定（並び・グループ順）

一覧の並び・グループ順のような「どう見せるか」の設定は、**サーバーに置く**
（`settings` テーブル、[02-data-model.md](02-data-model.md) 2.11）。

localStorage だけに持たせていたが、それだとブラウザや端末を変えるたびに
見え方が戻ってしまう。同じ人が同じデータを見ている以上、どこから開いても
同じ並びで出したい。

| 置き場 | 役割 |
|---|---|
| `settings` テーブル | 正本。`GET /api/settings` で全部返し、`PUT /api/settings` で送った鍵だけ上書きする |
| localStorage | 控え。**サーバーの応答が届くまで**と、**オフライン**のときに使う。鍵はサーバーと同じ名前 |

読む順は「控え → サーバー → このブラウザで選び直した値」で、後のものが勝つ
（`app/composables/useSettings.ts`）。

- 選び直した値を最優先にするのは、送っている最中に届いた応答には**その変更が
  入っていない**ため。優先しないと、選んだ直後に前の値へ戻る
- 保存はサーバーの応答を待たない。控えとこの場の表示はすぐ変え、送信だけ
  0.4 秒まとめて遅らせる（14.2 の3と同じ）
- 送れなかった分は残しておき、**繋がり直したときに送り直す**
  （`watchSettingsRetry`）。オフラインで選び直しても失われない
- 競合の確認はしない。後から書いたものが残る（見え方が揃えばよいため）

鍵はサーバーと localStorage で同じ名前を使う（`sort:items` /
`sort:items:group` のように画面ごと）。以前からブラウザに残っている値も
そのまま拾えるので、移し替えは要らない。
