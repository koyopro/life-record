# 14. クライアントの状態管理

編集した内容を、画面をまたいで即座に出すための決まりごと。

**編集した結果はストアに置く。画面はストアだけを読む。サーバーへの送信は
ストアが裏で行う。**

## 14.1 なぜ要るか

編集してから別の画面へ移り、戻ってくると編集前の内容が一瞬（電波が悪いと
数秒）見える、という問題が繰り返し起きていた。原因はどれも同じで、

- 画面が `useFetch` の結果とセッション内の控えの**2つ**を見ていた
- 書き込みは `$fetch` でサーバーへ送るだけで、**読み取り元を更新していなかった**
- 編集中の値がコンポーネントの `ref`（下書き）にあり、**画面を離れると消えた**

その結果「どちらか片方だけが新しい」状態ができ、戻ったときに古い方が出た。
場所ごとに手当てを足すと、手当ての数だけ抜けが残る。

## 14.2 決まりごと

### 1. 画面はストアだけを読む

`useFetch` / `$fetch` を `pages` と `components` に置かない。取得はストアの
`track()` の中だけで行い、結果もストアの控えへ入れる。読む場所が1つなら、
「片方だけ新しい」状態は作れない。

### 2. 書き込みもストアを通す

編集はストアの操作（`editTodayBody` など）を呼ぶ。ストアが控えへ即座に反映し、
送信を予約する。画面はサーバーの応答を待たない。

### 3. デバウンスするのは送信であって、ローカル反映ではない

打鍵はそのままストアへ渡す。遅らせるのは送信だけ
（`app/utils/save-scheduler.ts`）。

こうすると下書き（`xxxDraft`）が要らなくなり、「編集中はサーバーの内容で
上書きしない」というコンポーネント側の手当ても要らなくなる。遅延送信は
ストア（モジュール）に残るので、送る前に画面を移っても送信は続く。

### 4. サーバーの内容を重ねるとき、まだ送れていない本文は残す

取り直した内容を当てるときは、送信待ち・送信中の本文だけローカルを残し、
それ以外（日付・並び順・記録の増減・メタデータ）はサーバーを採る。丸ごと
捨てると、書いている最中に触っていない部分まで古いままになる。

`mergeServerItems`（IndexedDB 側）が未送信の変更を上書きしないのと同じ規則。

### 5. 写しは、写した先も一緒に更新する

`ItemDto.body` は先頭 Section の本文の写しで、IndexedDB にも入っている
（一覧の `Shift` + `C` でのコピー元、詳細を開いた直後の初期表示）。先頭
Section を保存したら、この写しも更新する。しないと、次にサーバーから
取り直すまで（最大30秒）古い本文が残る。

### 6. まだ Section が無い日の打鍵は、控えとは別に持つ

詳細で書く枠は**その日の Section** で、日をまたげば別の枠になる
（docs/03-functional-spec.md 3.2）。その日の記録がまだ無いうちは、打った内容を
ストアの下書き（`item-detail-today-draft`）へ置き、何か書かれた最初の送信で
Section を作る。

`ItemDto.body`（＝最初の Section の写し）に混ぜてはいけない。混ぜると、
過去に書いた記録が当日の枠に出てしまう。

## 14.3 層

```text
pages / components        読む（computed）／書く（ストアの操作）だけ
        ↓
ストア                     useItemStore      … TODO のメタデータ（IndexedDB が正）
                          useItemDetailStore … 作業記録（Section）
                          useDiaryStore      … 日記
        ↓ 即座に反映              ↓ 送信は遅らせて裏で
控え（useState + localStorage）   save-scheduler → API
IndexedDB                        SyncQueue → sync-engine → API
```

| ファイル | 役割 |
|---|---|
| `app/utils/save-scheduler.ts` | 鍵ごとの遅延送信。順序・失敗・保存状態を持つ。Vue 非依存 |
| `app/utils/section-order.ts` | Section の並び・先頭 Section・当日の枠の決め方（サーバーと同じ規則） |
| `app/composables/useToday.ts` | 「今日」。開いたまま日付をまたいだら切り替わる |
| `app/composables/usePersistedRecordCache.ts` | 控えの置き場（`useState` ＋ localStorage への書き戻し） |
| `app/composables/useItemDetailStore.ts` | 本文・作業記録の唯一の入口 |
| `app/composables/useDiaryStore.ts` | 日記の唯一の入口 |

## 14.4 TODO のメタデータとの違い

TODO のメタデータ（タイトル・状態・期限・タグ）は、IndexedDB を唯一の
読み取り元とし、送信は `SyncQueue` に積む（[12-offline.md](12-offline.md)）。
オフラインでも編集でき、送れなかった操作は残る。

本文（Section）と日記はサーバーにしか無いので、そこまではやらない。ストアの
控えは「取得が終わるまでの初期表示」と「編集した結果の置き場」であって、
未送信の操作を貯める場所ではない。

そのため、**ページごと消える瞬間（タブを閉じる・再読み込み・別サイトへ移る）
に送信が間に合わないことがある**。アプリの中で画面を移るだけなら、遅延送信は
ストアに残るので取りこぼさない。

ここを確実にするには、送るものを IndexedDB へ置いて次回に持ち越す必要が
あり、それは Section と日記をオフライン対応させる話になる
（[12-offline.md](12-offline.md) 12.9）。

## 14.5 状態管理ライブラリ

Pinia は入れていない。今回の問題は「置き場が無いこと」ではなく
「書き込みが読み取り経路を通っていないこと」だったため、層を整えるだけで
解消した。入口が `useXxxStore()` に揃っているので、必要になったときに
中身を差し替えれば移せる（[04-architecture.md](04-architecture.md) 4.3）。

## 14.6 テスト

`npm test`。画面から切り離せる層だけを対象にする。

- `tests/save-scheduler.spec.ts`: 途中の値を送らない、同じ鍵で追い越さない、
  失敗を握り潰さない、flush
- `tests/section-order.spec.ts`: 並びと先頭 Section が、サーバーと同じ結果になる
- `tests/offline/todo-repository.spec.ts`: 本文の写しの差し替え（`setItemBody`）

画面をまたぐ挙動（編集 → 別画面 → 戻る）はブラウザでの確認になる。取り直しの
最中を見たいので、DevTools の Network を Slow 3G にしてから行う。

1. 本文を書いて一覧へ戻り、開き直して編集前の本文が出ないこと
2. 書いた直後（1秒以内）に画面を移っても、サーバーに届いていること
3. 日記を書いて別の日へ移り、戻って編集前の本文が出ないこと
4. 日記を書いて一覧（カレンダー）へ戻り、プレビューが編集後になっていること
