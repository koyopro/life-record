# 12. オフライン対応

スマートフォンから使うことが多く、電波の悪い場所（移動中・地下）でも
TODO を見て、書けることを重視する。

**サーバーの PostgreSQL が正本**で、ブラウザの IndexedDB はその写しと、
まだ送れていない操作の置き場とする。IndexedDB を長期保存用のDBとしては
設計しない（消えても、サーバーから取り直せる）。

## 12.1 何ができるか

| 対象 | オフライン |
|---|---|
| アプリの起動 | できる（Service Worker） |
| TODO の一覧・絞り込み・並べ替え | できる |
| TODO の追加・編集・状態変更・削除・取り消し | できる（繋がったときに送る） |
| タグの付け外し | できる |
| 本文・作業記録（Section）の閲覧・編集 | できる（繋がったときに送る） |
| 日記の閲覧・編集 | できる（繋がったときに送る） |
| 一度見た画像の表示 | できる（中身を控えてある） |
| 検索・画像の追加 | **できない**（サーバー・S3 にしか無い） |

本文と日記も IndexedDB に持つ。**書いたものが手元に残らない場所を作らない**
ため。以前は Section と日記をサーバーだけに置いていたが、送信は打鍵から数百
ミリ秒遅れて走るので、その間にタブを閉じる・再読み込みすると書いた内容の
行き先が無くなっていた（[15-client-state.md](15-client-state.md)）。

手元に持つのは**開いたことのある分だけ**で、全件を先に落としてくることはない。

## 12.2 Service Worker

`@vite-pwa/nuxt`（Workbox）を使う。設定は `nuxt.config.ts` の `pwa`。

受け持つのは**アプリの起動だけ**で、TODO の中身は扱わない。

- precache するのは JS / CSS / HTML / アイコンなど、起動に要る静的ファイル
- **API の応答は Cache Storage に入れない**。動的なデータは IndexedDB を正規の
  置き場とし、通信が失敗したらアプリ側がそちらを読む
- 新しい版を入れたら、待たずに入れ替え（`skipWaiting` / `clientsClaim`）、
  古いキャッシュは消す（`cleanupOutdatedCaches`）

### オフラインでの起動（殻）

この構成では画面をサーバーで描いている（SSR）ため、オフラインでは
`/today` などの HTML を取れない。そこで **SSR しないページを1枚だけ静的に
書き出しておき**（`/offline-shell`）、画面への移動はすべてそれで受ける
（Workbox の `navigateFallback`）。

```text
オフラインで /today を開く
   ↓
Service Worker が /offline-shell の HTML を返す
   ↓
ブラウザ側で、いまの URL（/today）の画面を描く
   ↓
IndexedDB から一覧を読んで表示する
```

`/api/` と `/images/` は殻で受けない（素通しして失敗させる）。

## 12.3 IndexedDB

`idb` を使う。定義は `app/utils/offline/local-database.ts`。

| ストア | 内容 |
|---|---|
| `items` | TODO 本体（`ItemDto` + 同期状態 + 競合の基準） |
| `sections` | 作業記録（`SectionDto` + `itemId` + 同期状態）。Item ごと・日付ごとに引ける |
| `diaries` | 日記（日付が主キー。本文 + サーバーで見た更新日時 + 同期状態） |
| `operations` | まだ送れていない操作（積んだ順の通し番号が主キー） |
| `conflicts` | 競合を検出した記録。人に知らせるまで残す |
| `images` | 一度見た画像の中身（パスが主キー。[11-scrapbox-notation.md](11-scrapbox-notation.md) 11.7） |
| `meta` | 最終取得日時など |

Item の同期状態（`syncState`）は `synced` / `pending_create` / `pending_update` /
`pending_delete` の4つ。本文（Section・日記）は `synced` / `pending_save` /
`pending_delete` の3つで、**作成と更新を分けない**。本文は id（日記は日付）を
決めてから書くもので、送るときはどちらも「その id の内容をこれにする」という
同じ操作になるため。

構造を変えるときは `DB_VERSION` を上げ、`upgrade` に手順を足す。中身は
いつでもサーバーから取り直せるので、迷ったら作り直してよい。

### 層

コンポーネントから IndexedDB を直接触らない。

| 層 | 役割 |
|---|---|
| `local-database.ts` | 接続とスキーマ（LocalDatabase） |
| `freshness.ts` | 重ねるときの決まり（手元とサーバーのどちらが新しいか）。種類をまたいでここだけ |
| `todo-repository.ts` | TODO の読み書き・サーバーの内容の重ね方（TodoRepository） |
| `todo-actions.ts` | 「ローカルへ書く」と「操作を積む」を1組にしたもの |
| `body-repository.ts` | 本文（作業記録・日記）の読み書きと、サーバーの内容の重ね方 |
| `body-actions.ts` | 本文の「ローカルへ書く」と「操作を積む」を1組にしたもの |
| `sync-queue.ts` | 未送信の操作の列（SyncQueue） |
| `sync-runner.ts` | 操作1つの送信と、失敗の分類 |
| `sync-engine.ts` | 列を順に流し、結果をローカルへ反映する |
| `useItemStore` | 画面が見る唯一の入口（全件を持つ） |
| `useItemDetailStore` | 作業記録の入口。開いた Item の分だけ持つ |
| `useDiaryStore` | 日記の入口。開いた日の分だけ持つ |
| `useSync` | いつ流すか（オンライン復帰・画面復帰・操作の直後）と、画面への表示 |

## 12.4 データの流れ

読むとき。

```text
画面表示
  ↓
IndexedDB から即座に表示（待たせない）
  ↓
オンラインなら /api/items?status=all を1回だけ取る
  ↓
IndexedDB を更新（未送信の変更と、応答より後に送り終えた分は上書きしない）
  ↓
画面を更新
```

一覧ごとに条件を変えて取りに行くことはせず、**全件を1回**取る。
絞り込みと並べ替えはローカルで計算する（`useItemList` / `app/utils/item-order.ts`）。
そのため、オフラインでも「今日」「タスク」「タグ」の一覧がそのまま出せる。

初回アクセスで IndexedDB が空のときは、サーバー描画で受け取った内容を
そのまま最初の写しとして書き込む。

本文（作業記録・日記）は全件ではなく、**開いた分だけ**取る。詳細画面なら
その Item、日記ならその日を1回取って重ねる。手元にある分は取得を待たずに
出すので、オフラインでもそのまま読める。

日記の「この日にやったこと」も、**手元の作業記録から作る**。同じ日付の作業記録を
持つ Item を新しい順に並べるだけで、サーバー（`server/utils/diaries.ts`）と同じ
結果になる（[02-data-model.md](02-data-model.md) 2.8）。

そのため、`GET /api/diaries/:date` は**その日の作業記録そのもの**（どの Item の
ものかを添えたもの）も返し、手元へ重ねる。手元にあるのは詳細を開いたことの
ある Item の分だけなので、これが無いと**他の端末で書いた作業がその日の一覧に
出ない**。重ねる単位は Item ごとではなく日付ごと（`mergeServerSectionsOnDate`）。

開いたままにしている画面（詳細・日記）は、**タブに戻ってきたときにも取り直す**。
開いている間に別の端末で書かれた分を拾うため。

書くとき。

```text
ユーザーが操作する（完了・追加・タグ…／本文を1文字打つ）
  ↓
IndexedDB を更新（同期状態を pending_* にする）
  ↓
UI を即座に更新
  ↓
操作を列へ積む
  ↓
オンラインなら、そのまま送る（オフラインなら列に残る）
```

「保存できるまで待つ」画面は作らない。オンラインかどうかで呼び分けもしない。

本文は打鍵のたびにここを通る。ただし**列へ積むのは対象ごとに1つだけ**で、
送るのは入力が落ち着いてから（0.7秒）。送る内容は積んだ時点の値ではなく、
**送信の直前に手元から取り直す**ので、打った分はすべて最新の1回で届く。

## 12.5 競合

別の端末（あるいは同じ端末の別タブ）が先に変えている場合がある。

更新を送るときは、**こちらが最後に見たサーバーの `updatedAt`**
（`baseUpdatedAt`）を添える。サーバーは今の値と違えば `409` を返し、
今の内容を `data.item` に載せる（`server/api/items/[id].patch.ts`）。

方針は**新しい方を採る**。個人利用では、書いたものが黙って消えるのがいちばん
驚きが大きいため。

**手元の変更のほうが後**なら、サーバーの版を土台にして**送り直す**。

- 内容は手元のまま、競合の基準（`baseUpdatedAt`）だけサーバーに合わせる
- 送るのは**自分が変えた項目だけ**なので、他の端末が変えた別の項目は残る
  （題を向こうが、メモをこちらが直したなら、どちらも残る）
- 何も捨てていないので、知らせも出さない
- 送り直しは間を空ける。すぐ投げ直すと、相手が変え続けている間ずっと
  回り続ける。回数を数え、収まらなければ諦めて画面に出す（12.7 と同じ扱い）

**サーバーの変更のほうが後**なら、サーバーを採る。ただし黙って上書きしない。

- サーバーの内容をローカルへ採用する
- その Item に積まれていた未送信の操作は取り下げる
- **捨てたローカルの変更を `conflicts` に記録し、画面に出す**
  （「『◯◯』は他の端末の変更があったため、サーバー側の内容にしました」）

新旧は `updatedAt` で比べる。手元のものは書き換えた時刻（この端末の時計）、
サーバーのものは向こうが書き換えた時刻なので、**別の時計を比べている**。端末の
時計が大きくずれていると採る側が入れ替わりうるが、それでも「新しい方を採る」
ほうが、書いたものが黙って消えるより驚きが少ない。

載せ直した直後は、相手が変えた項目だけ手元が古いままになる（送り直しでは
自分の項目しか送らないため）。送り終えた直後に一覧を取り直すので、そこで揃う。

### 届いていた送信の送り直しは、競合ではない

応答が返らなかった送信は列に残って**送り直される**（12.6）。1回目が実は
届いていると、サーバーの `updatedAt` は進んでいるので **409 になる**。だが
中身は自分が送ったもので、他の端末の変更ではない。

そこでサーバー側を採ると、**自分の変更を自分で捨てる**ことになる。しかも
その Item の未送信の操作はまとめて取り下げられるので、応答を待つ間に書き足した
分（メモの続きなど）まで消える。

そのため、409 が返ったら**送ろうとした項目がすでにサーバーに入っているか**を
見る（`sync-engine.ts` の `alreadyApplied`）。入っていれば送り終えたものとして
扱い、競合の記録も残さない。見るのは送った項目だけで、触っていない項目が
違っていても構わない。

別のタブが同じ操作を送ったとき（Mac アプリのタブ・複数のウィンドウ）も同じ形に
なるので、まとめてここで吸収される。

自動でのマージ（本文の行ごとの突き合わせ、CRDT など）は行わない。**項目ごと**に
どちらを採るかが決まれば十分で、個人利用でそれ以上の複雑さは見合わないため。

サーバー側で消えていた場合（`404`）も競合として扱い、ローカルからも消して
その旨を知らせる。

削除はこの確認をしない。消すという指示は、間に他の変更があっても意図が
変わらないため。

**本文（作業記録・日記）は競合の確認をしない。**`baseUpdatedAt` を添えず、
最後に書いたものがそのまま残る。文章は項目ごとの突き合わせができず、どちらか
一方を捨てるしかない以上、「いま書いた方を残す」がいちばん驚きが少ない。
Item のメタデータで競合が起きたときも、本文の未送信の操作は取り下げない
（サーバーにまだ無いものを消してしまうため）。

送り先そのものが無いとき（`404`。他の端末で Item ごと消えたなど）は、
その操作を送り終えたものとして列から外し、手元の記録も残さない。

## 12.6 冪等性

「サーバーでは成功したが、応答を受け取る前に切れた」場合、同じ操作を
もう一度送る。二重に効かないよう、API 側で次を担保する。

| 操作 | 担保 |
|---|---|
| 追加（`POST /api/items`） | id はクライアントが決める。同じ id が来たら作らず、今あるものを返す |
| 更新（`PATCH /api/items/:id`） | 同じ値を入れ直すだけ。完了への遷移は「未完了→完了」のときだけ次回分を作る。送り直しが競合（409）になったときは、同じ内容が入っているかを見て成功として扱う（12.5） |
| 削除（`DELETE /api/items/:id`） | すでに無ければ `404`。クライアントは成功と同じに扱う |
| タグ（`POST /api/items/tags`） | 付ける・外すは集合の操作 |
| 復元（`POST /api/items/restore`） | すでに戻っていれば、そのまま返す |
| 本文（`PUT /api/sections/:id`） | **id はクライアントが決める**。同じ id なら作らずに上書きする（作成と更新を分けない） |
| 記録の削除（`DELETE /api/sections/:id`） | すでに無ければ `404`。クライアントは成功と同じに扱う |
| 並べ替え（`POST /api/sections/reorder`） | 渡された順に 0 から振り直すだけ |
| 日記（`PUT /api/diaries/:date`） | 日付が主キーの upsert。空なら消す |

操作には ID（`opId`）も振ってあり、どの送信がどの操作に対応するかを
クライアント側で追えるようにしている。

## 12.7 送信と再送

- 送るのは**列の先頭から1つずつ**。追い越すと、続けざまの操作
  （完了にしてすぐ取り消す）の前後が入れ替わる
- 順序は積んだ順の通し番号で持つ。時刻だと同じミリ秒の前後が決まらない
- **失敗しても操作は消さない**
- 一時的な失敗（通信断・5xx・認証切れ）は間隔を空けて送り直す
  （1秒 → 5秒 → 30秒 → 2分 → 10分）
- 5回で自動の送り直しはやめる（**無限には投げ続けない**）。操作は残したまま
  画面に「送れていません」と出し、押せば送り直せる
- 内容の問題（400 など）は、投げ続けても通らないのですぐ諦める
- ブラウザがオフラインだと分かっている間は送らない。試すだけ失敗の回数が
  増えて、諦める判断が早まってしまうため

## 12.8 画面での知らせ

普段は何も出さない。次のときだけ、小さく出す（`SyncStatus`）。

- オフライン: ヘッダーの下に「● オフライン」
- 未送信がある: 「未同期（n）」／送信中は「同期中…」
- 送れていない: 「送れていません（n）」＋「送り直す」
- 競合した: 何が起きたかを一行。閉じるまで残す

一覧のカードと詳細には「未同期」の印を出す。どのタスクがまだサーバーに
届いていないかが分かるようにするため。

オンラインかどうかの判定は `navigator.onLine`（電波の有無）だけに頼らず、
実際にサーバーへ届いたかどうかも合わせて見る。

## 12.9 オフラインで扱わないもの

- **検索**: `/api/search` はサーバーの全文検索に頼っており、手元には無い
- **画像の追加**: アップロードは S3 へ直接送るので、オフラインではできない
  （[11-scrapbox-notation.md](11-scrapbox-notation.md) 11.7）
  - **一度見た画像は出せる**。中身を IndexedDB に控えてあるため（11.7
    「中身を手元に控える」）。まだ見ていない画像は出せない
- **タグ一覧**: `/api/tags` が取れないときは、手元の Item から数えたもので代用する
  （並びと候補のためだけに使う）
  - **色だけは直近のものを localStorage に控える**（`datalake:tag-colors`）。
    手元の Item はタグの名前しか持たないため、控えが無いとリロードのたびに
    すべてのタグが既定の灰色になり、応答が届くまで数秒そのままになる。
    リロードは Service Worker が返す殻から始まり、サーバー描画の内容が
    無いところから組み立て直すため（12.2）
- **スマートリスト**（[08-todo-management.md](08-todo-management.md) 8.6）: 条件を
  localStorage に控えるので、オフラインでも開ける（中身は手元の Item から
  選び直すため）。作る・直す・消すのはオンラインのときだけ
- **画面の設定**（一覧の並び・グループ順）: 正本はサーバーだが、選んだ内容は
  localStorage にも控えるので、オフラインでも同じ見え方で開ける。オフラインの
  間に選び直した分は、繋がり直したときに送る
  （[15-client-state.md](15-client-state.md) 14.7）
- **まだ開いたことのない本文**: 本文は開いた分だけ手元に持つので、一度も
  開いていない Item の作業記録や日記は、オフラインでは出せない。ただし
  一覧カード用の写し（`ItemDto.body`）は全件ぶん持っているので、その Item に
  何が書いてあったかは一覧から読める
  - このとき、手元に記録が無いまま今日の枠へ書くと、**サーバーに既にある
    その日の記録とは別の記録**になる（id を手元で決めるため）。繋がった
    ときに両方が並ぶので、要らない方を消す

## 12.10 認証

アプリケーション側に認証は無く、Vercel の Deployment Protection でサイト全体を
守っている（[04-architecture.md](04-architecture.md) 4.6）。したがって
**トークンなどの認証情報を IndexedDB に置くことはない**。

保護の Cookie はブラウザが持つ。オフラインでも Service Worker が起動を担い、
IndexedDB の中身は同じ端末の同じオリジンからしか読めないため、オフライン
利用のために新しく持つものは無い。

Cookie が切れた状態で送ると `401` / `403` が返る。この場合は操作を消さず、
入り直せば送れるものとして送り直しの対象に残す。

## 12.11 テスト

`npm test`（vitest + fake-indexeddb）。`tests/offline/`。

- `freshness.spec.ts`: 重ね方の決まり（未送信は残す・応答より後に送り終えた分は
  残す・それ以外はサーバーを採る）。TODO も本文もこの1つを使う
- `todo-repository.spec.ts`: サーバーの内容の重ね方（未送信を上書きしない・
  古い応答で戻さない・消えたものを消す）、競合の記録の掃除
- `sync-queue.spec.ts`: 積んだ順、待機中の追い越し防止、失敗しても消さない、
  回数切れで諦める、取り消し
- `sync-runner.spec.ts`: 失敗の分類（通信断 / 5xx / 401 / 404 / 409 / 400）
- `sync-scenarios.spec.ts`: オンライン・オフライン・復帰・競合の筋道
  （二重登録が起きないこと、届いていた送信の送り直しで自分の変更を捨てないこと、
  取り直しと保存が前後しても巻き戻らないことを含む）
- `body-repository.spec.ts`: 本文の重ね方（未送信を上書きしない・古い応答で
  戻さない・消えたものを消す）、日付ごとの重ね方（他の端末で書かれた作業記録を
  手元へ写す・別の日付には触らない）
- `body-sync.spec.ts`: 打鍵をまとめて1つの操作にする、オフラインで書いて
  繋がってから送る、送るのは送信時点の内容、削除・並べ替え・日記の筋道

Service Worker まわりは実際のブラウザでの確認になる。

```bash
npm run build && npm run preview
```

1. 一度開いてから、DevTools の Network を Offline にして再読み込みできること
2. オフラインで追加・編集・状態変更ができ、「未同期」が出ること
