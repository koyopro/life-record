# 12. オフライン対応

スマートフォンから使うことが多く、電波の悪い場所（移動中・地下）でも
TODO を見て、書けることを重視する。

**サーバーの PostgreSQL が正本**で、ブラウザの IndexedDB はその写しと、
まだ送れていない操作の置き場とする。IndexedDB を長期保存用のDBとしては
設計しない（消えても、サーバーから取り直せる）。

## 12.1 何ができるか

| 対象 | オフライン |
|---|---|
| アプリの起動 | できる（Service Worker） |
| TODO の一覧・絞り込み・並べ替え | できる |
| TODO の追加・編集・状態変更・削除・取り消し | できる（繋がったときに送る） |
| タグの付け外し | できる |
| 本文・作業記録（Section） | **できない**（サーバーにしか無い） |
| 日記・検索・画像 | **できない** |

Section と日記を持たないのは、IndexedDB に置くものを最小限にするため。
一覧に出るぶんの本文（`ItemDto.body`）は写しに含まれるので、読むことはできる。

## 12.2 Service Worker

`@vite-pwa/nuxt`（Workbox）を使う。設定は `nuxt.config.ts` の `pwa`。

受け持つのは**アプリの起動だけ**で、TODO の中身は扱わない。

- precache するのは JS / CSS / HTML / アイコンなど、起動に要る静的ファイル
- **API の応答は Cache Storage に入れない**。動的なデータは IndexedDB を正規の
  置き場とし、通信が失敗したらアプリ側がそちらを読む
- 新しい版を入れたら、待たずに入れ替え（`skipWaiting` / `clientsClaim`）、
  古いキャッシュは消す（`cleanupOutdatedCaches`）

### オフラインでの起動（殻）

この構成では画面をサーバーで描いている（SSR）ため、オフラインでは
`/today` などの HTML を取れない。そこで **SSR しないページを1枚だけ静的に
書き出しておき**（`/offline-shell`）、画面への移動はすべてそれで受ける
（Workbox の `navigateFallback`）。

```text
オフラインで /today を開く
   ↓
Service Worker が /offline-shell の HTML を返す
   ↓
ブラウザ側で、いまの URL（/today）の画面を描く
   ↓
IndexedDB から一覧を読んで表示する
```

`/api/` と `/images/` は殻で受けない（素通しして失敗させる）。

## 12.3 IndexedDB

`idb` を使う。定義は `app/utils/offline/local-database.ts`。

| ストア | 内容 |
|---|---|
| `items` | TODO 本体（`ItemDto` + 同期状態 + 競合の基準） |
| `operations` | まだ送れていない操作（積んだ順の通し番号が主キー） |
| `conflicts` | 競合を検出した記録。人に知らせるまで残す |
| `meta` | 最終取得日時など |

同期状態（`syncState`）は `synced` / `pending_create` / `pending_update` /
`pending_delete` の4つ。

構造を変えるときは `DB_VERSION` を上げ、`upgrade` に手順を足す。中身は
いつでもサーバーから取り直せるので、迷ったら作り直してよい。

### 層

コンポーネントから IndexedDB を直接触らない。

| 層 | 役割 |
|---|---|
| `local-database.ts` | 接続とスキーマ（LocalDatabase） |
| `todo-repository.ts` | TODO の読み書き・サーバーの内容の重ね方（TodoRepository） |
| `todo-actions.ts` | 「ローカルへ書く」と「操作を積む」を1組にしたもの |
| `sync-queue.ts` | 未送信の操作の列（SyncQueue） |
| `sync-runner.ts` | 操作1つの送信と、失敗の分類 |
| `sync-engine.ts` | 列を順に流し、結果をローカルへ反映する |
| `useItemStore` | 画面が見る唯一の入口（全件を持つ） |
| `useSync` | いつ流すか（オンライン復帰・画面復帰・操作の直後）と、画面への表示 |

## 12.4 データの流れ

読むとき。

```text
画面表示
  ↓
IndexedDB から即座に表示（待たせない）
  ↓
オンラインなら /api/items?status=all を1回だけ取る
  ↓
IndexedDB を更新（未送信の変更は上書きしない）
  ↓
画面を更新
```

一覧ごとに条件を変えて取りに行くことはせず、**全件を1回**取る。
絞り込みと並べ替えはローカルで計算する（`useItemList` / `app/utils/item-order.ts`）。
そのため、オフラインでも「今日」「Inbox」「タグ」の一覧がそのまま出せる。

初回アクセスで IndexedDB が空のときは、サーバー描画で受け取った内容を
そのまま最初の写しとして書き込む。

書くとき。

```text
ユーザーが操作する（完了・追加・タグ…）
  ↓
IndexedDB を更新（同期状態を pending_* にする）
  ↓
UI を即座に更新
  ↓
操作を列へ積む
  ↓
オンラインなら、そのまま送る（オフラインなら列に残る）
```

「保存できるまで待つ」画面は作らない。オンラインかどうかで呼び分けもしない。

## 12.5 競合

別の端末（あるいは同じ端末の別タブ）が先に変えている場合がある。

更新を送るときは、**こちらが最後に見たサーバーの `updatedAt`**
（`baseUpdatedAt`）を添える。サーバーは今の値と違えば `409` を返し、
今の内容を `data.item` に載せる（`server/api/items/[id].patch.ts`）。

MVP での方針は**サーバー優先**。ただし黙って上書きしない。

- サーバーの内容をローカルへ採用する
- その Item に積まれていた未送信の操作は取り下げる
- **捨てたローカルの変更を `conflicts` に記録し、画面に出す**
  （「『◯◯』は他の端末の変更があったため、サーバー側の内容にしました」）

自動でのマージ（項目ごとの突き合わせ、CRDT など）は行わない。個人利用で
競合はまれであり、複雑さに見合わないため。

サーバー側で消えていた場合（`404`）も競合として扱い、ローカルからも消して
その旨を知らせる。

削除はこの確認をしない。消すという指示は、間に他の変更があっても意図が
変わらないため。

## 12.6 冪等性

「サーバーでは成功したが、応答を受け取る前に切れた」場合、同じ操作を
もう一度送る。二重に効かないよう、API 側で次を担保する。

| 操作 | 担保 |
|---|---|
| 追加（`POST /api/items`） | id はクライアントが決める。同じ id が来たら作らず、今あるものを返す |
| 更新（`PATCH /api/items/:id`） | 同じ値を入れ直すだけ。完了への遷移は「未完了→完了」のときだけ次回分を作る |
| 削除（`DELETE /api/items/:id`） | すでに無ければ `404`。クライアントは成功と同じに扱う |
| タグ（`POST /api/items/tags`） | 付ける・外すは集合の操作 |
| 復元（`POST /api/items/restore`） | すでに戻っていれば、そのまま返す |

操作には ID（`opId`）も振ってあり、どの送信がどの操作に対応するかを
クライアント側で追えるようにしている。

## 12.7 送信と再送

- 送るのは**列の先頭から1つずつ**。追い越すと、続けざまの操作
  （完了にしてすぐ取り消す）の前後が入れ替わる
- 順序は積んだ順の通し番号で持つ。時刻だと同じミリ秒の前後が決まらない
- **失敗しても操作は消さない**
- 一時的な失敗（通信断・5xx・認証切れ）は間隔を空けて送り直す
  （1秒 → 5秒 → 30秒 → 2分 → 10分）
- 5回で自動の送り直しはやめる（**無限には投げ続けない**）。操作は残したまま
  画面に「送れていません」と出し、押せば送り直せる
- 内容の問題（400 など）は、投げ続けても通らないのですぐ諦める
- ブラウザがオフラインだと分かっている間は送らない。試すだけ失敗の回数が
  増えて、諦める判断が早まってしまうため

## 12.8 画面での知らせ

普段は何も出さない。次のときだけ、小さく出す（`SyncStatus`）。

- オフライン: ヘッダーの下に「● オフライン」
- 未送信がある: 「未同期（n）」／送信中は「同期中…」
- 送れていない: 「送れていません（n）」＋「送り直す」
- 競合した: 何が起きたかを一行。閉じるまで残す

一覧のカードと詳細には「未同期」の印を出す。どのタスクがまだサーバーに
届いていないかが分かるようにするため。

オンラインかどうかの判定は `navigator.onLine`（電波の有無）だけに頼らず、
実際にサーバーへ届いたかどうかも合わせて見る。

## 12.9 オフラインで扱わないもの

- **本文・作業記録（Section）**: サーバーから取れていないときは編集させない。
  書いたものの行き先が無くなるため、その旨を詳細画面に出す。
  ただし取得の最中には出さない（出してすぐ消すと、その分だけ画面がずれる）。
  オフラインだと分かっているときは即座に、オンラインのつもりなのに返って
  こないときは数秒待ってから、小さく1行で知らせる
- **日記・検索・画像**: これまでどおりオンラインのみ
- **タグ一覧**: `/api/tags` が取れないときは、手元の Item から数えたもので代用する
  （並びと候補のためだけに使う）

## 12.10 認証

アプリケーション側に認証は無く、Vercel の Deployment Protection でサイト全体を
守っている（[04-architecture.md](04-architecture.md) 4.6）。したがって
**トークンなどの認証情報を IndexedDB に置くことはない**。

保護の Cookie はブラウザが持つ。オフラインでも Service Worker が起動を担い、
IndexedDB の中身は同じ端末の同じオリジンからしか読めないため、オフライン
利用のために新しく持つものは無い。

Cookie が切れた状態で送ると `401` / `403` が返る。この場合は操作を消さず、
入り直せば送れるものとして送り直しの対象に残す。

## 12.11 テスト

`npm test`（vitest + fake-indexeddb）。`tests/offline/`。

- `todo-repository.spec.ts`: サーバーの内容の重ね方（未送信を上書きしない・
  消えたものを消す）、競合の記録の掃除
- `sync-queue.spec.ts`: 積んだ順、待機中の追い越し防止、失敗しても消さない、
  回数切れで諦める、取り消し
- `sync-runner.spec.ts`: 失敗の分類（通信断 / 5xx / 401 / 404 / 409 / 400）
- `sync-scenarios.spec.ts`: オンライン・オフライン・復帰・競合の筋道
  （二重登録が起きないことを含む）

Service Worker まわりは実際のブラウザでの確認になる。

```bash
npm run build && npm run preview
```

1. 一度開いてから、DevTools の Network を Offline にして再読み込みできること
2. オフラインで追加・編集・状態変更ができ、「未同期」が出ること
3. Offline を解いたら送られ、「未同期」が消えること
4. もう一度 `npm run build` して開き直しても壊れないこと（古いキャッシュが
   残らないこと）
