## Q2. DBアクセス方式

| 案 | 長所 | 短所 |
|---|---|---|
| Drizzle ORM + `@neondatabase/serverless` | 軽量。SQL に近く移行しやすい。型がスキーマから導出される | ORM としての機能は Prisma より薄い |
| Prisma | 機能が豊富。マイグレーション管理が強い | バンドルサイズが大きく、サーバーレスでは重くなりがち |
| 生SQL + `@neondatabase/serverless` | 依存が最小。移行が最も容易 | 型付けとマイグレーションを自前で管理する必要がある |

**現時点の推奨: Drizzle ORM + `@neondatabase/serverless`**

通常の `pg` による TCP コネクションプールは、Vercel Functions のライフサイクルと相性が悪いため避ける。

→ Milestone 1 で確定させる。

## Q3. 認証方式

個人利用・単一ユーザー前提。過剰な仕組みは不要だが、インターネット公開である以上、必ず必要。

| 案 | 長所 | 短所 |
|---|---|---|
| パスワード + セッションCookie（自前） | 依存が最小。外部サービスに縛られない | 実装と運用を自分で持つ |
| Auth.js (NextAuth / @sidebase/nuxt-auth) + Google OAuth | パスワード管理が不要。実装が少ない | ライブラリ・Google への依存 |
| Vercel の Deployment Protection | 実装ゼロ | Hobby プランでは Preview のみ等の制約があり、Production の保護には有料プランが必要 |
| Cloudflare Access 等の外部認可レイヤ | 実装ゼロ | 構成に別ベンダーが増える |

**現時点の推奨: Google OAuth（自分のアカウント1つのみ許可）** — パスワードを自分で保持しなくてよく、スマートフォンからのログインも楽なため。

初期段階では DB に `user_id` を持たせない。将来マルチユーザー化する場合は全テーブルに追加する。

→ Milestone 1 で確定、Milestone 2 で実装。

## Q4. 画像の配信方式

S3 バケットはパブリックアクセスを全ブロックする方針。その上での配信方法。

| 案 | 長所 | 短所 |
|---|---|---|
| API 経由で都度、署名付き取得URLを発行 | バケットを非公開のまま維持できる。実装が単純 | 表示のたびにAPI呼び出しが必要。URLに有効期限があるため、本文にURLを直接埋め込めない |
| CloudFront + 署名付きCookie/URL | 配信が速い。キャッシュが効く | 構成が増える。設定が複雑 |
| API をリバースプロキシにして画像を返す | URL が固定でき、本文に直接埋め込める | Vercel Function を画像が通過するため、帯域と実行時間を消費する |

日記を含むため、**推測可能な公開URLは採用しない**。

本文には S3 のオブジェクトキー（または内部ID）を埋め込み、表示時に解決する方式が有力。
本文に有効期限付きURLを直接書き込むと、期限切れで画像が失われるため避ける。

→ Milestone 6 で確定させる。

## Q6. Item の分類手段

**これは元の仕様書との間で解消が必要だった最大の論点。**

元の仕様書では `Section` を「Item を分類するカテゴリ（プロジェクト / 買い物 / アイデア等）」として定義していたが、
データモデルでは `Section` を「Item に紐づく、日付付きの作業記録」として定義しており、意味が完全に異なる。

**データモデル側を正とした結果、現在のデータ構造には Item を分類する手段が存在しない。**

整理は以下の2軸のみで行われる。

- `status`（inbox / backlog / in_progress / closed）
- Section による作業記録の蓄積

### 検討すべきこと

まず「分類が本当に必要か」を、実際に使いながら判断する。
Milestone 2 の日常利用を通じて、Inbox の整理に分類軸が要ると感じた時点で導入を検討する。

導入する場合の候補:

| 案 | 内容 |
|---|---|
| タグ | `tags` テーブル + `item_tags` 中間テーブル。柔軟だが管理が煩雑になりやすい |
| プロジェクト | `projects` テーブル + `items.project_id`。1対多で単純。元の仕様書の「Section」に近い |
| ラベル文字列 | `items.label text`。最も単純。正規化しないので表記ゆれが起きる |

**先に決めない。** 実運用で必要性が確認されてから導入する（[06-roadmap.md](06-roadmap.md) Milestone 9）。

## Q7. Item の本文（クイックメモとの整合）

Item は `title` のみを持ち、本文を持たない。
一方、Google Keep 的な「素早くメモを取る」用途では、タイトルだけでは足りない場面がある。

**方針:** メモの内容は、Item 作成と同時に作られる **当日付の Section** に書く。

```text
Item.title   = メモの見出し（または冒頭）
Section.body = メモの内容（date = 作成日）
```

これによりデータモデルを変更せずにクイックメモを表現できる。
「タイトルだけ」「タイトル + 本文」の両方を、同じ入力画面から出せるようにする。

→ 詳細は [03-functional-spec.md](03-functional-spec.md) 3.1、実装は Milestone 2。

## Q9. 日本語全文検索

データ量が小さいうちは `ILIKE` による部分一致で足りる。

将来的に PostgreSQL の全文検索を使う場合、日本語では標準の `to_tsvector` が機能しにくく、`pg_bigm` や `pgroonga` といった拡張が必要になる。
**Neon でこれらの拡張が利用できるかは要確認。** 利用できない場合は、`ILIKE` + trigram (`pg_trgm`) での代替を検討する。

→ Milestone 7 で確認する。
