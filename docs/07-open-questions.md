# 07. 未確定事項・検討中の論点

## 確定済みの前提

議論を整理する前提として、以下は確定している。

- データ構造は [02-data-model.md](02-data-model.md) を正とする
- Item に `type` カラムは持たせない
- 構成は Vercel + Neon + Vue.js + TypeScript + S3
- フロントエンドは **Nuxt 4**（Q1 決定済み）

## Q1. フロントエンド構成（Vite + Vue SPA / Nuxt）

> **決定: Nuxt 4 を採用する。**

Vue.js を使うことは確定していた。その上での構成として以下を比較した。

| 案 | 構成 | 長所 | 短所 |
|---|---|---|---|
| A | Vite + Vue 3 (SPA) + Vercel Functions | 構成が薄い。フロントとAPIの責務が明確 | API とフロントで型共有の仕組みを自前で用意する必要がある |
| B | Nuxt 3/4 + Nitro server routes | Vercel との親和性が高い。API・ルーティング・型共有が一体 | フレームワークの学習・追従コスト。SSR は個人用途では過剰 |

B を採用。個人開発で書く総量が減り、画面・API・型定義が1プロジェクトで完結するため。

## Q2. DBアクセス方式

> **決定: Drizzle ORM + `@neondatabase/serverless` を採用する。**
> 開発中はローカル PostgreSQL に対して `node-postgres` ドライバで接続する。

| 案 | 長所 | 短所 |
|---|---|---|
| Drizzle ORM + `@neondatabase/serverless` | 軽量。SQL に近く移行しやすい。型がスキーマから導出される | ORM としての機能は Prisma より薄い |
| Prisma | 機能が豊富。マイグレーション管理が強い | バンドルサイズが大きく、サーバーレスでは重くなりがち |
| 生SQL + `@neondatabase/serverless` | 依存が最小。移行が最も容易 | 型付けとマイグレーションを自前で管理する必要がある |

Drizzle を採用。型がスキーマから導出でき、生成物が軽く、SQL に近いため移行時の負担が小さい。

本番の Vercel Functions では、通常の `pg` による TCP コネクションプールはライフサイクルと相性が悪いため避け、
`@neondatabase/serverless` を使う。ローカル開発では通常の `pg` ドライバを使い、`DATABASE_URL` で切り替える。

## Q3. 認証方式

> **決定: Vercel の Deployment Protection を使う。アプリケーション側に認証は実装しない。**
>
> **要確認（デプロイ前のブロッカー）:** Vercel の Deployment Protection は、
> Hobby プランでは Preview デプロイのみが対象で、**Production の保護には Pro プランが必要**な可能性がある。
> 公開前に必ずプラン側の対応範囲を確認すること。Production を保護できない場合は、
> 下表の別案（パスワード + セッションCookie / Google OAuth）へ切り替える。

個人利用・単一ユーザー前提。過剰な仕組みは不要だが、インターネット公開である以上、必ず必要。

| 案 | 長所 | 短所 |
|---|---|---|
| パスワード + セッションCookie（自前） | 依存が最小。外部サービスに縛られない | 実装と運用を自分で持つ |
| Auth.js (NextAuth / @sidebase/nuxt-auth) + Google OAuth | パスワード管理が不要。実装が少ない | ライブラリ・Google への依存 |
| Vercel の Deployment Protection | 実装ゼロ | Hobby プランでは Preview のみ等の制約があり、Production の保護には有料プランが必要 |
| Cloudflare Access 等の外部認可レイヤ | 実装ゼロ | 構成に別ベンダーが増える |

Deployment Protection を採用。アプリ側の実装がゼロで済み、個人利用には十分なため。

初期段階では DB に `user_id` を持たせない。将来マルチユーザー化する場合は全テーブルに追加する。

## Q4. 画像の配信方式

> **決定: 本文には `/images/<ID>.<拡張子>` を書き、アプリがその都度
> 署名付きの取得URLへリダイレクトする。**

S3 バケットはパブリックアクセスを全ブロックする方針。その上での配信方法。

| 案 | 長所 | 短所 |
|---|---|---|
| API 経由で都度、署名付き取得URLを発行 | バケットを非公開のまま維持できる。実装が単純 | 表示のたびにAPI呼び出しが必要。URLに有効期限があるため、本文にURLを直接埋め込めない |
| CloudFront + 署名付きCookie/URL | 配信が速い。キャッシュが効く | 構成が増える。設定が複雑 |
| API をリバースプロキシにして画像を返す | URL が固定でき、本文に直接埋め込める | Vercel Function を画像が通過するため、帯域と実行時間を消費する |

日記を含むため、**推測可能な公開URLは採用しない**。

本文に有効期限付きURLを直接書き込むと、期限切れで画像が失われるため避ける。

### 採用した形

1件目（都度、署名付き取得URLを発行）を、**リダイレクトで**行う。
表の「本文にURLを直接埋め込めない」という短所は、本文に書くのを
アプリ内のパスにすることで消える。

```text
本文            [/images/<ID>.png]      ← 期限もホスト名も入らない
  ↓ 表示
GET /images/<ID>.png                    ← アプリ（Vercel Function）
  ↓ 302
S3 の署名付き取得URL（5分）             ← ブラウザが直接取りに行く
```

- バケットは非公開のまま維持できる
- 本文は期限のない固定パスなので、書き換えが要らない
- 画像バイナリは Function を通らない。3件目（リバースプロキシ）の
  短所である帯域・実行時間の消費が起きない
- リダイレクト自体は `no-store`。指し先が期限つきのため

オブジェクトキーは `images/<ID>.<拡張子>` とし、本文のパスと1対1に対応させる。
対応表（画像メタデータテーブル）を持たずに解決できる。

CloudFront は、必要になってから足せる（本文を書き換えずに差し替えられる）。

## Q5. バックアップの実行方式

> **決定: GitHub Actions で毎日 `pg_dump` を取り、S3 へ置く。**
> 定義は `.github/workflows/backup.yml`。

| 案 | 長所 | 短所 |
|---|---|---|
| GitHub Actions で `pg_dump` → S3 | 実行環境の制約が少ない。ログが残る | GitHub への依存 |
| Vercel Cron | 構成が増えない | Function の実行時間制限がある。`pg_dump` バイナリの利用が難しい |
| 手元のマシンで手動 / cron | 依存が最小 | 実行忘れが起きる |

GitHub Actions を採用した。Vercel Cron は Function の実行時間制限があり、
`pg_dump` のバイナリも置きにくい。手元の cron は実行忘れに気づけない。

**ダンプの置き場所は、画像用とは別のバケットにする。** 同じ鍵で
両方に触れると、片方の事故がもう片方に及ぶため。

- `pg_dump --format=custom` で取る。`pg_restore` で部分復元ができる
- `workflow_dispatch` を付けて手でも回せるようにする。
  復元の練習と、取れているかの確認のため
- 失敗の通知は GitHub の「Actions が失敗したらメール」に任せる

## Q6. Item の分類手段

> **決定: タグを導入する。** 詳細は [09-tags.md](09-tags.md)。
>
> 1つの Item が複数の観点に属することが実際に多く、プロジェクト（1対多）では
> どちらか一方を選ばされるため。RTM のタグ運用をそのまま持ち込めることも決め手。

**これは元の仕様書との間で解消が必要だった最大の論点。**

元の仕様書では `Section` を「Item を分類するカテゴリ（プロジェクト / 買い物 / アイデア等）」として定義していたが、
データモデルでは `Section` を「Item に紐づく、日付付きの作業記録」として定義しており、意味が完全に異なる。

**データモデル側を正とした結果、現在のデータ構造には Item を分類する手段が存在しない。**

整理は以下の2軸のみで行われる。

- `status`（inbox / backlog / in_progress / closed）
- Section による作業記録の蓄積

### 検討した案

| 案 | 内容 | 判断 |
|---|---|---|
| **タグ** | `tags` テーブル + `item_tags` 中間テーブル | **採用** |
| プロジェクト | `projects` テーブル + `items.project_id`。1対多で単純 | 複数の観点に属せないため不採用 |
| ラベル文字列 | `items.label text`。最も単純だが表記ゆれが起きる | リネームできないため不採用 |

`status`（進行状態）とタグ（内容による分類）は役割が異なるため、両者は併存する。

SmartAdd の `#` もタグとして解釈する（[09-tags.md](09-tags.md) 9.4）。
実装は [06-roadmap.md](06-roadmap.md) Milestone 4。

## Q7. Item の本文（クイックメモとの整合）

Item は `title` のみを持ち、本文を持たない。
一方、Google Keep 的な「素早くメモを取る」用途では、タイトルだけでは足りない場面がある。

**方針:** メモの内容は、Item 作成と同時に作られる **当日付の Section** に書く。

```text
Item.title   = メモの見出し（または冒頭）
Section.body = メモの内容（date = 作成日）
```

これによりデータモデルを変更せずにクイックメモを表現できる。
「タイトルだけ」「タイトル + 本文」の両方を、同じ入力画面から出せるようにする。

→ 詳細は [03-functional-spec.md](03-functional-spec.md) 3.1、実装は Milestone 2。
