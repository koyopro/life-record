# 05. 非機能要件・長期運用

## 5.1 最重要方針

このサービスで最も重要な非機能要件は、**長期間データを保持できること**。

個人用サービスなので、高可用性や大規模スケールは追求しない。その代わり、以下を重視する。

- データの永続性
- 定期バックアップ
- DB・画像データのエクスポート可能性
- サービス終了・移行時にデータを取り出せること
- 特定サービスへの過度な依存を避けること

日記・画像を含むため、**10年以上の保持**を前提に設計する。

## 5.2 バックアップ

### DB (Neon)

- Neon の Point-in-Time Restore / ブランチ機能を把握しておく（プランにより保持期間が異なる）
- それとは別に、**自分の手元に残る形のバックアップ**を持つ
  - `pg_dump` による定期ダンプ
  - ダンプの保存先は S3（DB とは別ベンダー）またはローカル
- プラットフォーム側の機能のみに依存しない

### 画像 (S3)

- バケットのバージョニングを有効化する（誤削除・上書き対策）
- ライフサイクルルールで自動削除しない（長期保持が目的のため）
- 別リージョンまたは別ストレージへの複製を検討する

### 実行方法

**GitHub Actions で毎日 `pg_dump` を取り、S3 へ置く**（[07-open-questions.md](07-open-questions.md) Q5）。
定義は `.github/workflows/backup.yml`。

```text
毎日 03:00 JST
  → pg_dump --format=custom
  → s3://<バックアップ用バケット>/db/datalake-YYYYMMDD.dump
```

**ダンプの置き場所は、画像用とは別のバケットにする。**
同じ鍵で両方に触れると、片方の事故がもう片方に及ぶため。

必要な Secrets は workflow のコメントに書いてある。

## 5.3 エクスポート

サービスから離れる可能性を常に想定し、以下を取り出せる状態にしておく。

| 対象 | 形式 |
|---|---|
| Item / Section / Diary | SQL ダンプ、および JSON / テキスト |
| 画像 | S3 上のオブジェクトをそのまま取得 |

特に **テキストへのエクスポート**を重視する。Section と Diary の本文は Scrapbox 記法の
プレーンテキストとして保存されるため（[11-scrapbox-notation.md](11-scrapbox-notation.md)）、
日付ごとのファイル群として書き出せば、そのまま読める形で持ち出せる。
Scrapbox へ取り込む場合も、記法をそろえてあるため変換がほぼ不要。

### エンドポイント

| URL | 形式 |
|---|---|
| `/api/export` | JSON。構造をそのまま。読み込み直せる |
| `/api/export?format=text` | プレーンテキスト。日付ごとに読める形 |

どちらもブラウザで開けばファイルとして落ちる。
画像は本文に `/images/<ID>.<拡張子>` として残るだけなので、
実体はバケットごとコピーする（`aws s3 sync`）。

## 5.4 復元

バックアップは、**復元できることを確認して初めて意味を持つ**。

### 手順

新規の Neon ブランチへ復元し、本番に触れずに中身を確かめる。

```bash
# 1. Neon で新しいブランチを作り、その接続文字列を控える
# 2. S3 からダンプを取ってくる
aws s3 cp s3://<バックアップ用バケット>/db/datalake-YYYYMMDD.dump .

# 3. 復元する（--clean は付けない。空のブランチに入れるため）
pg_restore --no-owner --no-acl --dbname "<復元先の接続文字列>" \
  datalake-YYYYMMDD.dump

# 4. 中身を確かめる
psql "<復元先の接続文字列>" \
  -c 'SELECT count(*) FROM items' \
  -c 'SELECT count(*) FROM sections' \
  -c 'SELECT count(*) FROM diaries'
```

画像は S3 のバケットをまるごと同期して確認する。

```bash
aws s3 sync s3://<画像用バケット>/images ./images-restore
```

### 確認の運用

**四半期に1度、上の手順を実際に通す。**
バックアップが壊れていることに気づけるのは、復元したときだけなので。

- GitHub Actions のログで、毎日ダンプが取れていることを確認する
  （失敗すれば GitHub からメールが来る）
- 復元まで通したら、確認した日を Item として残す
  （繰り返し設定 `*every 3 months` で回す）

## 5.5 可用性・パフォーマンス

- 単一ユーザーのため、同時アクセスはほぼ発生しない
- コールドスタートによる初回応答の遅さは許容する
- データ量は年単位でも小規模に留まる想定。初期段階でのパフォーマンス最適化は行わない
- ただし、スマートフォンからの Item 追加だけは体感速度を重視する（楽観的UI更新等を検討）

## 5.6 セキュリティ

- 全 API エンドポイントで認証を必須とする
- S3 バケットはパブリックアクセスを全ブロックする
- 認証情報・接続文字列は Vercel の環境変数で管理し、リポジトリにコミットしない
- 日記という性質上、URL の推測による第三者アクセスが起きない設計にする（画像URLを含む）

## 5.7 コスト

想定される維持費。

| サービス | 想定 |
|---|---|
| Vercel | Hobby プラン（無料）で足りる想定 |
| Neon | 無料枠で足りる想定。データ量が小さいため |
| S3 | 従量課金。画像の総量次第だが、個人利用では月あたり極小 |
| ドメイン | 任意 |

無料枠に依存しすぎると、プラン変更時に影響を受ける。長期利用を前提とするため、有料化しても継続できる程度のコストに収まっているかを定期的に確認する。
